# Editable DOCX Export and Configurable Taxonomy Design

Date: 2026-07-24
Status: Implemented and regression-tested

## 1. Goals

1. Replace the web UI's PDF export action with an editable `.docx` export.
2. Preserve the current two-level organization: primary domain and secondary problem type.
3. Let the user add or remove taxonomy options in an independent classification-management view, implemented as a dedicated right-side drawer so the review page remains available underneath.
4. Persist taxonomy configuration in a local JSON file.
5. Store exactly one primary-domain/secondary-type pair as tags on every problem.
6. Filter both the current batch and the published asset library by those tags.

## 2. Non-goals

- Custom taxonomy entries do not participate in automatic classification.
- A problem cannot have multiple classification pairs.
- Taxonomy rename and drag-and-drop ordering are not included.
- The legacy PDF backend and existing PDF files are not deleted. The normal web UI no longer exposes PDF export.
- Complex diagrams are not converted to editable Word drawing objects.

## 3. Chosen Architecture

Use `python-docx` for document generation, a versioned JSON file for taxonomy configuration, and the existing `problems.category_group` and `problems.category_key` database columns as the canonical problem tags.

This avoids a second taxonomy database that could disagree with the requested JSON file. It also avoids moving searchable tag values into opaque JSON columns.

## 4. Taxonomy Configuration

### 4.1 File

Store the configuration at:

`<data_dir>/taxonomy.json`

On first startup, if the file does not exist, seed it from the current built-in `TAXONOMY`. The system fallback pair (the existing Chinese "uncategorized" group and category) remains reserved and is not presented as a removable entry.

Example schema:

```json
{
  "version": 1,
  "revision": 3,
  "groups": [
    {
      "id": "builtin-group-counting",
      "name": "\u8ba1\u6570",
      "source": "builtin",
      "active": true,
      "categories": [
        {
          "id": "builtin-category-coloring",
          "name": "\u67d3\u8272\u95ee\u9898",
          "source": "builtin",
          "active": true
        }
      ]
    }
  ]
}
```

Rules:

- `version` controls schema compatibility.
- `revision` increments after every successful save and supports optimistic concurrency.
- IDs are immutable. Built-in IDs are deterministic; custom IDs are generated by the server.
- Built-in and newly created custom names are Unicode NFKC-normalized and trimmed. For those entries, a group name is unique across active and archived non-historical groups, and a category name is unique within its group across active and archived non-historical categories.
- Imported `source=historical` names preserve their exact database values byte-for-byte so filter values continue to match existing SQL rows. Historical entries are immutable, always archived, and bypass new-name normalization, reserved-name, length, and character validation.
- Exact historical group names are coalesced into one archived group. Exact historical category names are unique within that exact group. Raw names that are NFKC-equivalent but not byte-identical remain distinct historical entries.
- A normalized new name may not exactly equal an existing historical raw name. NFKC-equivalent but byte-distinct historical values may coexist because they remain archived and are queried by exact SQL values.
- Existing API length constraints apply to built-in/custom writes: group at most 12 characters and category at most 24 characters.
- Empty names, control characters, path separators, and reserved fallback names are rejected for built-in/custom entries.
- Limit the file to 50 groups and 100 categories per group. Limit the PUT body to 256 KiB.
- A PUT cannot remove, rename, re-parent, or change the `source` of an existing ID. It may change `active`, or append a server-issued custom entry.
- New groups/categories are submitted with `id: null` and `source: "custom"`. The server validates all existing IDs first, assigns IDs to new parent groups before their children, writes the result, and returns the complete configuration with generated IDs. Clients replace their draft with that response.
- An archived group cannot contain an active child.
- File writes use a temporary file, `fsync`, and atomic replacement.
- Revision validation, write, directory `fsync`, and in-memory refresh occur under a process mutex and an OS file lock.
- Before replacing a valid existing file, retain one recovery backup at `taxonomy.json.bak`.
- On startup, a damaged main file is restored only from a validated backup. If both files are invalid, use built-in defaults in read-only degraded mode, expose the exact file error, and block taxonomy writes until the file is corrected. Never overwrite both invalid files automatically.

After database schema migration, and on every service startup, reconcile distinct `category_group/category_key` pairs from the database into the taxonomy configuration:

- Values present in the built-in taxonomy need no extra entry.
- Unknown existing values are added as `source=historical`, `active=false`.
- An unknown group and all of its historical children are archived.
- This import is idempotent by the exact raw `(category_group, category_key)` pair and does not rewrite problem rows. Distinct raw pairs remain distinct even if their NFKC forms are equal.
- If `taxonomy.json` already exists, newly discovered unknown pairs are appended as archived historical entries through the same validated atomic-write path before the API starts serving requests.
- The legacy `category` column is not used as an independent source after the existing storage migration has populated `category_group/category_key`. Future writes continue synchronizing `category=category_key`.

Taxonomy mutation and problem-tag writes share one application-level reentrant lock:

- `PUT /api/taxonomy` holds it while checking the revision, writing the file, and swapping the in-memory configuration.
- Manual acceptance, bulk acceptance, and category edits hold it from active-pair validation through the database write.
- Automatic processing may classify from an immutable snapshot, but must revalidate the selected pair under this lock immediately before storage. If it was archived meanwhile, the result becomes uncategorized and requires manual classification.
- This gives one local-process linearization point, matching the application's single-process deployment model.

### 4.2 Delete Means Archive

Deletion sets `active=false`; it does not erase the entry.

- Archived entries disappear from review/edit selectors.
- Historical problem tags are unchanged.
- Filters include archived entries that are still referenced and append a localized "inactive" label.
- Archiving a group archives all child categories.
- A confirmation dialog reports how many problems currently use the group or category.
- Unsaved panel changes can be canceled.

### 4.3 Automatic Classification

Automatic classification may choose only active built-in entries.

- Rule candidates whose output category is archived are excluded.
- Rule, Ollama, and cloud visual classification receive the same immutable active-built-in snapshot from a `TaxonomyService` injected into the processor/recognition services.
- Ollama/cloud prompts include only active built-in entries.
- Custom entries are omitted from automatic-classification candidates.
- The legacy `categories` table and `Storage.category_names()` are not used to build automatic-classification candidates.
- If the only matching built-in result is archived, classification falls back to the reserved uncategorized pair and records a non-critical reason that manual classification is needed.
- Manual review selectors include all active built-in and custom entries.

## 5. Taxonomy APIs

Add:

- `GET /api/taxonomy`
  - Returns the full active/archived configuration, current revision, and per-entry usage counts.
- `PUT /api/taxonomy`
  - Accepts the complete edited configuration plus `expected_revision`.
  - Validates it, atomically writes JSON, refreshes the in-memory taxonomy, and returns the new revision.
  - Returns HTTP 409 if the revision is stale.

Keep `GET /api/categories` as a compatibility endpoint, but derive its active selector payload from the taxonomy service.

Filtering endpoints accept only a taxonomy pair or an exact pair returned by a distinct database query, allowing real historical values without accepting arbitrary input. Every acceptance/publishing path, including cleaned, normalized, reconstructed, bulk acceptance, and manual category changes, validates that the pair is currently active. A previously accepted archived pair remains published and filterable, but must be reassigned to an active pair before a later re-accept operation.

## 6. Independent Classification-management View

Add a localized "Manage categories" button to the web toolbar. It opens a dedicated right-side drawer with its own header, body, save, cancel, and close controls. This drawer is the independent management window; it does not mix editing controls into individual problem cards and does not navigate away from the review page.

The panel contains:

- Primary-domain list.
- Expandable secondary-type lists.
- Add-domain and add-type actions.
- Archive actions with usage-count confirmation.
- Clear visual treatment for built-in, custom, active, and archived entries.
- Localized "Save changes" and "Cancel" actions.
- Inline validation errors that explain the exact conflict.

The panel edits a local draft. Only "Save changes" calls `PUT /api/taxonomy`. After success:

- Refresh review selectors and both filter selectors.
- Preserve a currently selected filter if it remains valid.
- If the selected filter is newly archived, keep it available as an archived historical filter.
- Do not silently change any problem's tags.

All category names are untrusted display data. The frontend must render them through `textContent` or a context-correct HTML/attribute escaping helper everywhere they appear, including management rows, selector options, confirmation text, and problem tag chips. No category value may be interpolated into executable HTML or JavaScript.

## 7. Problem Tags and Filtering

Exactly one pair is stored per problem:

- `category_group`: primary-domain tag.
- `category_key`: secondary-type tag.

The legacy `category` column remains synchronized with `category_key` for compatibility.

Public problem responses add:

```json
{
  "tags": {
    "category_group": "\u8ba1\u6570",
    "category_key": "\u67d3\u8272\u95ee\u9898",
    "active": true
  }
}
```

No new tag table is required.

Behavior:

- A problem card displays the two values as tag chips.
- Manual save validates the pair against active taxonomy entries.
- Publishing/accepting preserves the chosen pair.
- Current-batch rendering and asset-library queries both support the same two-level filters.
- Secondary options are restricted by the selected primary domain.
- Historical archived values remain filterable.
- Existing problem rows require no destructive migration because their canonical tag columns already exist.

## 8. DOCX Export

### 8.1 User-facing Behavior

Replace:

- The current localized "Export A4 PDF" button with "Export Word DOCX".
- The current localized partial-export button with "Skip pending and export DOCX".

Eligibility intentionally follows the current PDF contract but enforces complete tags: a problem must have `selected_artifact`, non-empty `category_group` and `category_key`, a synchronized legacy `category`, non-empty `ocr_text`, and either `status == "ready"` or `review_status == "accepted"`. The row's exact stored pair is sufficient for an already accepted historical tag; it does not need to be active. The standard action fails if any batch item is ineligible. Partial export includes only eligible items.

The export is generated from the current batch, as the PDF export is today.

### 8.2 Document Structure

Use A4 portrait pages and set the Word East Asian font reference to `Microsoft YaHei`. DOCX generation does not depend on the font being installed on the server; the editing computer performs font resolution and may substitute a fallback.

Document order:

1. Editable document title and generation metadata.
2. A Word table-of-contents field configured for heading levels 1 and 2.
3. Primary domain as Heading 1.
4. Secondary type as Heading 2, including problem count.
5. Problems in stable batch order within each secondary type.

Word document settings request field updates on open. If a client does not update the TOC automatically, the headings still provide navigation and the user can update the field manually.

### 8.3 Problem Layout

- Maximum two problems are started on one page.
- Category headings do not count toward the two-problem limit.
- Insert a hard page break after every second problem.
- A long problem may naturally flow to additional space/pages; content must never be clipped or scaled to unreadable size.
- Each problem has editable title and body paragraphs followed by an initial blank-answer paragraph block.
- The initial blank-answer height is 45 mm in the exporter constant for version 1; it is not a new web setting.
- The initial blank space is a normal editable Word element, not a rasterized area.
- Diagrams are inserted proportionally and constrained to page width.
- Do not insert a whole-question screenshot when structured content is available.

### 8.4 Text, Equations, and Images

Use the existing ordered `content_blocks`:

- `text`: editable Word runs/paragraphs.
- Supported `latex`: convert into native editable Office Math (OMML).
- `image`: insert the referenced figure or precise formula fallback crop.

The LaTeX-to-OMML converter supports only the same validated deterministic subset accepted by content blocks, initially:

- Numbers and Latin variables.
- Arithmetic and comparison operators.
- Exact generated commands such as `\times`, `\div`, `\le`, and `\ge`.

Version 1 deliberately does not claim support for parentheses, powers, subscripts, roots, or fractions because the current content-block detector does not generate them as LaTeX blocks.

The exporter parses a strict grammar into a small internal equation AST and constructs OMML from XML elements with escaped text; it never concatenates untrusted text into raw XML.

- Every existing `latex` block must include `source_text` and pass the strict parser. The converter is total for that accepted grammar.
- As part of this feature, extend the content-block fallback detector so newly processed or explicitly reprocessed math-like spans outside the supported LaTeX grammar become precise `image` blocks. The current detector is not assumed to cover every complex formula.
- For a version-1 older record, the exporter applies a deterministic conservative check to `text` blocks: the exact unsupported mathematical symbols U+221A SQUARE ROOT, U+2211 N-ARY SUMMATION, U+222B INTEGRAL, U+2248 ALMOST EQUAL TO, and U+2260 NOT EQUAL TO, or an explicit TeX command beginning with a backslash, require a positioned image block. If such a token remains in text and source coordinates are unavailable, DOCX export stops on that problem with a concrete request to reprocess it. Generic punctuation such as braces, carets, and underscores alone does not trigger rejection.
- A malformed legacy LaTeX block without a fallback image stops export with a concrete reprocessing request; it is never omitted or emitted as malformed math.
- A future content-block version may add an explicit `fallback_asset` to LaTeX blocks, but implementation must not pretend that version 1 already has one.

Each source block must be consumed exactly once. The exporter rejects missing or unsafe image resources and reports the problem filename and block index.

### 8.5 Storage and Download

Use the existing `exports` table:

- `kind = "docx"`
- UUID export ID
- generated filename
- absolute server-side file path under `<data_dir>/exports`

Generate each export under a new UUID-backed server filename so concurrent exports from the same batch cannot share or overwrite a path. Keep the descriptive filename only as the download name. Generate to a temporary file in the export directory, validate it as an Office Open XML ZIP, `fsync`, and atomically replace the UUID target before inserting the export record. If the export-record insert fails, delete that newly generated target. The generic download endpoint maps allowed kinds to a MIME whitelist; `docx` uses `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.

Add:

- `POST /api/batches/{batch_id}/export-docx`
- Reuse `GET /api/exports/{export_id}` for download with the existing path and symlink protections.

The old PDF endpoints remain for compatibility but are no longer called by the web UI.

## 9. Error Handling

Errors must be concrete and actionable:

- Taxonomy parse error identifies the local file and parsing cause.
- Revision conflict asks the user to reload the panel.
- Invalid pair identifies both submitted values.
- DOCX export lists the first ineligible problem or invalid content block.
- Formula conversion failure falls back to an image when one exists; otherwise export fails rather than losing content.
- Missing Microsoft YaHei on the server does not block export because DOCX stores a font reference. Word may substitute a font on a client that lacks Microsoft YaHei.

## 10. Testing

### Taxonomy

- First-run seeding preserves all current default entries.
- First-run seeding imports unknown database tag pairs as archived historical entries without rewriting problem rows.
- Historical imported names remain byte-identical and exact SQL filtering still finds their original rows.
- Add custom group/type, restart, and verify persistence.
- Archive a used category; historical problem remains tagged and filterable.
- Archived category is absent from review selectors.
- Archiving a group archives all children.
- Active built-in categories remain eligible for automatic classification.
- Archived and custom categories are excluded from automatic classification.
- Invalid main JSON restores a valid backup; two invalid files enter read-only degraded mode without overwrite.
- Atomic-save, process/file locking, request limits, and stale-revision behavior.
- Concurrent archive versus manual, bulk, and automatic tag writes obeys the shared-lock linearization rule.
- Duplicate and reserved names are rejected.
- Existing IDs cannot be removed, renamed, re-parented, or assigned a different source through PUT.
- New entries with null IDs receive server IDs, including children of a newly added parent.

### Tags and Filters

- Manual acceptance persists both tag values.
- Legacy `category` remains synchronized.
- Current-batch and asset views filter identically.
- Secondary filter options follow the selected primary domain.
- Archived historical tags display and filter correctly.

### DOCX

- Generated archive is a valid Office Open XML document.
- Concurrent exports of the same batch use distinct server paths and cannot overwrite each other.
- A failed export-record insert removes its newly generated file.
- Title, headings, text, and native equation nodes are editable.
- Supported LaTeX becomes OMML.
- Unsupported formulas and diagrams use the correct image blocks.
- The expanded fallback detector converts newly processed unsupported math spans into image blocks.
- Old text blocks containing unsupported math without coordinates fail with a reprocessing request.
- Malformed legacy LaTeX without a fallback fails with a reprocessing message.
- Older valid text-only content blocks export without forced reprocessing.
- No content block is duplicated or omitted.
- Page breaks occur after at most two started problems; headings do not consume a slot.
- Long questions are not clipped.
- Standard export blocks pending problems.
- Partial export includes only eligible problems.
- Download uses export IDs and rejects missing, traversal, and symlink targets.

### Regression

- Existing image processing, review, publishing, Markdown export, and legacy PDF endpoint tests remain passing.
- Existing accepted assets and category tags require no destructive migration.
- Archived and unknown historical tag pairs retain their original grouping in PDF, Markdown, and DOCX.
- Existing PDF and Markdown download records remain downloadable after the DOCX MIME whitelist is added.
- Malicious custom names such as `<img src=x onerror=alert(1)>` render only as text in management, filters, and problem cards.
